# Improvement: cache the OAuth token on non-macOS runners

Status: **ToDo** (filed 2026-11-06)

## Problem

`ws1_lib/WorkSpaceOneImporterBase.py` persists the WS1 OAuth token and its renewal timestamp between recipes by
calling `/usr/bin/security add-generic-password` / `find-generic-password` against a dedicated macOS Keychain
(`get_password_from_keychain`, `set_password_in_keychain`, `oauth_keychain_init`).

On Linux runners (e.g. a GitHub-hosted `ubuntu-latest` runner used to run the pruner recipes from a private CI/CD repo)
`/usr/bin/security` does not exist, so the save silently fails and every recipe requests a brand new token:

```
WorkSpaceOnePruner: Oauth client credentials were supplied, proceeding to use these.
WorkSpaceOnePruner: OAuth token issued at: 2026-11-06T11:22:45+00:00
WorkSpaceOnePruner: OAuth token should be renewed after: 2026-11-06T12:16:45+00:00
WorkSpaceOnePruner: OAuth token could not be saved in dedicated keychain
WorkSpaceOnePruner: OAuth token renewal timestamp could not be saved in dedicated keychain
```

Observed in a scheduled pruner run on a Linux runner (2026-11-06): 24 pruner recipes → 24 token requests in ~2 minutes.

## Impact

* Functionally harmless today - each recipe gets a valid token and completes.
* Unnecessary load on the WS1 OAuth token endpoint; risk of hitting rate limits as the recipe list grows or when the
  importer/assigner recipes are also moved to Linux runners.
* Two noisy log lines per recipe at verbosity 2.

## Proposed solution

Add a platform-neutral fallback cache used when the Keychain is unavailable (`sys.platform != "darwin"` or
`/usr/bin/security` missing):

1. Store `oauth_token` and `oauth_token_renew_timestamp` in a small JSON file under the AutoPkg cache dir, e.g.
   `<CACHE_DIR>/ws1_oauth_token.json`, created with mode `0600`.
2. Reuse the existing renewal-threshold logic unchanged - only the storage backend differs.
3. Keep the Keychain as the preferred backend on macOS; select the backend once in `oauth_keychain_init` (or a new
   `oauth_cache_init`) rather than at each read/write.
4. Downgrade the "could not be saved in dedicated keychain" messages to verbosity 3 when the fallback is in use, and
   log once at verbosity 2 which backend was selected.
5. Document in `README.md` that on non-macOS the token is cached on disk in `CACHE_DIR`, and that the cache dir
   should therefore not be committed or uploaded as an artifact unprotected.

Alternative considered: passing the token between recipes via an environment variable. Rejected because AutoPkg runs
each recipe in the same process but the env is reset per recipe, and CAR workers are separate processes.

## Acceptance criteria

* A multi-recipe run on Linux logs exactly one `OAuth token issued at` line (until the renewal threshold passes).
* macOS behaviour is unchanged (Keychain still used).
* Unit tests in `tests/` cover the file backend: write, read, expiry/renewal, and missing/corrupt file.
