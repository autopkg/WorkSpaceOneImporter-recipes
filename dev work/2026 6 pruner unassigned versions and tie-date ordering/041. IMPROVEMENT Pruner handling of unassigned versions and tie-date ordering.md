# IMPROVEMENT: WorkSpaceOnePruner – unassigned versions and tie-date ordering

Findings from reviewing a scheduled pruner dry-run on a Linux runner (2026-11-06),
`ws1_app_versions_prune=dry_run`, 24 pruner recipes.

## 1. Versions without an assignment are skipped and accumulate forever

`WorkSpaceOnePruner.py` derives the deployment date from
`assignments[0].distribution.effective_date` of the assignment-rules API response.
When an app version has **no assignment rules** this raises `IndexError` and the
version is logged and skipped:

```
Failed to find deployment date in Assignments, skipping version:<version>...!
```

Observed in the run:

* iTerm2 – 9 versions skipped (all pre-dating the assigner recipe, never assigned)
* LexmarkUniversalDriverColor – versions 2.1.0 and 2.2.0 skipped

Consequences:

* Skipped versions are never counted in `num_versions_found` and never marked
  `TO BE PRUNED`, so they stay in the console indefinitely – the opposite of what
  the pruner is for. Unassigned versions are in fact the *safest* candidates to prune.
* The `found N versions` summary under-reports what is actually in WS1.

Suggested improvement:

* Fall back to another date when no assignment exists, e.g. the app's
  `CreatedOn` / `ModifiedOn` field from the search result, or treat unassigned versions
  as *oldest* so they sort first and are pruned before any assigned version.
* Alternatively add an input (`ws1_prune_unassigned`, default `True`) so operators can
  choose whether unassigned versions are pruned first or left alone.
* Report skipped versions in the summary so the gap is visible in CI logs.

## 2. Tie-dated versions sort non-deterministically

`app_list.sort(key=lambda x: x["date"])` sorts on the **date only** (the time part is
deliberately dropped). When two versions were assigned on the same day the relative
order is whatever the WS1 search API returned, which is not guaranteed.

Observed in the run: PaloAltoNetworksGlobalProtect 6.3.3.650 and 6.3.3.1121 both
dated 2025-09-22. If they straddle the `keep_versions` boundary, which one is pruned
is effectively arbitrary.

Suggested improvement:

* Use a composite sort key: `(date, version)` with a proper version comparison
  (`packaging.version.Version` or AutoPkg's `APLooseVersion`), so the lower version is
  always considered older.
* Or keep the full ISO timestamp for sorting and only truncate for display.

## 3. Note on `Deployment date found in assignment #0`

The code assumes assignment rule #0 is the earliest deployment. If multiple assignment
rules exist (e.g. staged QA → PROD rollout) the first rule may not be the earliest
effective date. Consider taking `min(effective_date)` across all assignments.

## Scope

All changes are in `ws1-processors/WorkSpaceOnePruner.py`; no override or recipe
changes required. Should be tested with `ws1_app_versions_prune=dry_run` first.
