# Prompt

> Plan the change (design only, for review before implementation): WorkSpaceOneAssigner should assign each ring the
> newest version that has completed its full delay, instead of only ever working on the latest version.

# Design

## Problem (observed 2026-11-13, client AutoPkg CICD)

`WorkSpaceOneAssigner` only targets the **latest** version (`find_latest_app_version`). The rings are added
cumulatively to that version as `day0 + distr_delay_days` passes, where day-0 is the `effective_date` of its rule #0.
A newer release becomes the new "latest" and restarts the clock. When the release cadence is <= the PROD delay, PROD
never moves:

| App | Cadence | PROD delay | PROD stuck on | Duration |
|---|---|---|---|---|
| Firefox ESR | ~14 d | 14 d | 140.13.0 (day-0 07-22) | ~4 months |
| Edge | 2-4 d | 4 d | 155.0.4283.45 (day-0 10-09) | ~6 weeks |

This showed up only when `WorkSpaceOnePruner`'s keep-N window reached the stuck PROD version and the safeguard fired.

### WS1 behaviour relied on (documented by Omnissa, confirmed by observation)

Omnissa docs, [Internal Application Versions](https://docs.omnissa.com/MobileApplicationManagement-VSaaS/InternalApplicationVersions/)
(section "Maintain Multiple Versions of Your Internal Application"):

> Workspace ONE UEM can replace an internal application on devices, but it does not deploy multiple versions to
> devices. You can have multiple active versions in the console for management.

> If multiple versions of an app are available at different levels of the organization group (OG) hierarchy, the
> system first locates the OG closest to the device. It then selects the highest-assigned app version within that
> OG and provides it to the device.

> If you do not select Retire Previous Version, and you add an application version, Workspace ONE UEM assigns the
> higher App Version to devices.

The same page says "Note: macOS does not support downgrading to a lower version of an app", and describes
"Versioning Example - Beta Testing": a beta version for beta users alongside a non-beta version for regular users,
which is the ring model used here.

Consequences for this design:
- A device in several assigned groups gets the **highest** version assigned to any of its groups. This matches the
  observed counts: 140.13.0 went 433 → 0 once 153.6.0 got PROD, and 157.0.4341.57 went to 0 once .60 got
  TESTING/QA.
- So assigning PROD to an *older* version while a newer one holds TESTING/QA is safe. TESTING/QA devices stay on
  the newer one, and PROD-only devices get the older, soaked one.
- "Highest" is evaluated within the OG closest to the device, so all versions of an app must live in the same OG.
  Confirmed by the operator (2026-11-20): all imported versions of an app sit in one OG.
- No downgrade on macOS supports the "never downgrade a ring" condition below.

Related Omnissa docs:
- [Assign Applications to your macOS Devices](https://docs.omnissa.com/SoftwareDistributionManagement-VSaaS/AssignApplicationstoyourmacOSDevices/):
  assignment settings (Deployment Begins = `effective_date`, App Delivery Method, Keep App Updated Automatically,
  Display in App Catalog) and "The Priority setting takes precedence when there are conflicting deployments
  assigned to a single device" (priority between the assignments of *one* version).
- [Deploy Internal macOS Applications](https://docs.omnissa.com/SoftwareDistributionManagement-VSaaS/DeployInternalmacOSApplications/):
  upload and deployment options for macOS internal apps (Munki-based software distribution).

Assignment inheritance: the versions page says a new version inherits assignments from the preceding one
("Assignments Copied From") when added in the console. Confirmed by the operator (2026-11-20) and by the assigner
logs ("No existing Assignment Rules found"): versions imported through the API by WorkSpaceOneImporter arrive
without assignment rules. This design does not rely on inheritance.

## Proposed behaviour

Per ring `i` (rule index in `ws1_app_assignments`, ascending priority), the target is:

> the **newest** version (by `AppVersion` tuple, the same comparison as `find_latest_app_version`) that
> 1. already holds ring `i-1` (strict chain, see option B below), and
> 2. has `day0 + distr_delay_days[i] <= today`, and
> 3. is **not older** than the newest version already holding ring `i` (never downgrade a ring).

Ring 0 (TESTING, delay 0) keeps today's behaviour: always the latest version, day-0 = today if it has no rules.

Rules stay **cumulative per version**: a version that gets ring `i` is sent rules `0..i`, with effective dates
`day0 + delay` (always <= today, so never future-dated, which preserves the "future effective_date hides previous
versions" protection). That is exactly the shape the code produces today; it now also applies to versions other
than the latest.

### Option A vs option B for condition 1
- **A, date only:** any version with `day0 + delay_i <= today`. Simpler, but PROD can get a build that never
  reached QA, and rules `0..i-1` would have to be added retroactively.
- **B, strict chain (recommended):** the version must have actually held the previous ring. PROD only gets
  builds that QA ran. Matches the intent of staged rings and the existing cumulative rule shape.

### Expected effect
- Edge (QA 1 d, PROD 4 d): PROD trails the latest by one release, always a build that sat >= 4 days since day-0
  and went through QA.
- Firefox ESR: PROD gets 153.7.0 on 11-25 even if 153.8.0 arrives first.
- A dry check against today's state (11-20) changes nothing. Edge .60 and Firefox 153.6.0 already hold PROD (the
  manual promotion), and 153.7.0 is not eligible until 11-25.

## Implementation outline (`ws1-processors/WorkSpaceOneAssigner.py`)

1. `find_latest_app_version` → `find_app_versions`: return **all** matching macOS versions sorted newest-first.
   Keep `find_latest_app_version` as a thin wrapper (V1 simple mode and outputs keep using it).
2. New `get_assignment_rules(uuid)`: GET V2 rules per version (one call per version; ~10-12 for Edge, the same as
   the pruner does already). Extract:
   - `day0` = rule #0 `effective_date` (date part, same parsing as now),
   - which rings it holds, identified by **`distribution.name`** matching the recipe input ring name (TESTING / QA
     / PROD), not by position or tag, so console-made promotions (like the 11-20 manual fix) are recognised for
     the "never downgrade" check,
   - tag state: `#AUTOPKG`, `#AUTOPKG_DONE`, or untagged.
3. New pure function `plan_ring_targets(versions, ring_specs, today) -> {version_uuid: highest_ring_to_hold}`.
   No I/O, so it is fully unit-testable.
4. Apply loop: for each version needing a change, reuse the existing `ws1_app_assign_v2` body, refactored to
   accept the target ring count and day-0 instead of deriving them. **`copy.deepcopy(app_assignments)` per
   version**, because the current code mutates the input (`del smart_group_names`, `del distr_delay_days`,
   description suffixes).
5. Respect existing guards per version: untagged (manual) rules = hands off that version, but still counted for
   "never downgrade". `#AUTOPKG_DONE` = complete. Keep the `#AUTOPKG` / `#AUTOPKG_DONE` tagging unchanged.
6. Reporting: `ws1_importer_summary_result` lists every version promoted with its new ring(s), e.g.
   `157.0.4341.60: [2: PROD]; 158.0.4370.33: [0: TESTING]`. Same report fields, so Slacker needs no change.
   Output vars `ws1_app_uuid` / `ws1_app_id` stay = latest version.
7. Log at verbose 1 one line per ring: `Ring [PROD] target [157.0.4341.60] (day-0 11-16, eligible 11-20)`, so
   the rollout state is visible in CI logs.

### Edge cases
- Version without any rules (imported before the assigner existed, or not yet assigned): not a candidate for ring
  >= 1 (no day-0, not in chain). It is only a ring-0 candidate if it is the latest.
- Non-ascending delays in the recipe (e.g. QA 3 > PROD 1): the effective delay for ring `i` is
  `max(delay_0..delay_i)`, equivalent to today's "break at first future rule".
- ESR line switch (140.x → 153.x): version-tuple ordering handles it, and 153.x outranks 140.x.
- `ApplicationName in NAME` substring match: unchanged (out of scope, the same as the pruner).

## Decisions (operator review, 2026-11-20)
1. **Option B, strict chain:** PROD is only assigned to versions that have gone through QA.
2. **Behaviour switch:** input `ws1_assignment_strategy` = `newest_eligible` (**default**) | `latest_only`
   (previous behaviour, a rollback path without reverting code).
3. **Dry run:** input `ws1_assign_dry_run` (default `False`): log the plan, make no changes in WS1.
4. Staleness alert (3 to 4 x PROD delay, Slack only): optional, **not** part of this change.

## As built (branch `assigner-newest-eligible-per-ring`)

Differences from the outline above, found while implementing:

- **"Gone through QA" is taken literally:** a version gets ring `i` only if it held ring `i-1` *before* this run,
  so it moves up at most one ring per run. After an outage it catches up one ring per run, instead of getting QA
  and PROD at the same moment. Exception: rings with the same (effective) delay as the previous ring are meant to
  go out together and are assigned in the same run (e.g. two rings with delay 0).
- **Ring detection:** rules made by the processor (all tagged `#AUTOPKG`) are cumulative and in ring order, so
  they are counted by position, as before. A version with `#AUTOPKG_DONE` holds all rings. Only for rules made or
  changed by hand are rings recognised, by `distribution.name` **or** by the rule covering all smart groups of the
  ring. The smart group check is needed because a manual console promotion can have any name. The shape of
  existing rules (`name`, `description`, `smart_groups` as a UUID list, `effective_date`) was taken from real
  verbose assigner logs.
- **Scan is bounded:** versions are read newest-first and the scan stops at the newest version holding the final
  ring. Nothing older is ever changed, which also keeps the number of API calls low (typically 2 to 4 GETs per
  app instead of one per version).
- The pure planning function is `plan_ring_promotions(versions, ring_specs, today) -> (promotions, ring_report)`.
  Supporting functions: `describe_version_rules`, `build_assignment_rules`, `resolve_ring_specs`,
  `get_assignment_rules`, `put_assignment_rules`, `ws1_app_assign_v2_newest_eligible`.
- **`latest_only` runs the previous code path unchanged** (`ws1_app_assign_v2`), apart from honouring dry run.
  The new path does not share its body, so the rollback path is really the old behaviour.
- Promotions are applied oldest version first, so the later rings (PROD) are served first if a call fails midway.
- Log lines at verbose 1, one per ring: `Ring [2: PROD] will be assigned to version [x]` or
  `Ring [2: PROD] stays on version [x]`, then `Successfully set assignment rules [2: PROD] for [app] version [x]`
  or `DRY RUN: would set assignment rules ...`. At verbose 2, one line per version scanned with the rings it
  holds, its day-0 and whether AutoPkg manages it.
- Dry run also covers the simple (V1) assignment mode.
- Unchanged quirk: ring 0 needs `distr_delay_days: '0'`. Day-0 is the day of the first assignment, so a first
  ring with a delay is never assigned (same as before).

Verified offline: 37 unit tests in `tests/ws1_processors/test_assigner_ring_promotion.py`, Black, isort and
flake8 clean. **Not yet verified against a live WS1 tenant**: do the dry run below first.

## Testing
- New offline unit tests `tests/ws1_processors/test_assigner_ring_promotion.py`, following the pattern of
  `tests/shared_processors` (AutoPkg's Python, `autopkglib` import).
  - `plan_ring_promotions`: the Edge and Firefox treadmill sequences above (taken from the real 11-06 to 11-20 logs),
    never-downgrade after a manual promotion, unassigned versions, non-ascending delays, single-ring recipe.
  - Apply loop with mocked `requests`: correct rules payload per version, deepcopy (input not mutated across
    versions), untagged version left alone.
- Live: dispatch the assigner with `ws1_assign_dry_run` for Edge and Firefox at verbose 2, compare
  the plan with expectations, then a normal run.

## Rollout
1. Upstream commit (processor + tests + CHANGELOG + wiki page `ws1_app_assignments`: explain ring promotion).
2. Client AutoPkg CICD: the processor hash changes, so all assigner overrides fail trust → the trust-info PR flow
   (`trust-info-assigner-<date>`) creates the PR, review and merge it.
3. Watch the assigner logs for 2 weeks: the PROD ring target should advance for Edge every few days.
4. Follow-ups, separate changes: pruner improvements (skip assigned versions instead of aborting, note 041), then
   the optional staleness alert.
